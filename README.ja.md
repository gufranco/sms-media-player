## 概要

任意の動画ファイルをMaster Systemカートリッジに変換するベイカーと、それを改造なしのコンソールでフルスクリーン表示するZ80プレイヤーです。ベイカーはホストで動作し、プレイヤーとすべてのROMビルドはバージョンを固定したDockerイメージ内で動作します。

前処理、エンコーダー、バンクへのパッキング、Z80プレイヤー、操作系まで、全工程が動作します。

| 構成要素 | 状態 |
|---|---|
| エンコーダーとワーキングセットのポリシー | 動作中。小数点以下5桁まで一致するリプレイオラクルを備えています |
| 映像 | 256x192、ラスター全体です。異なる縦横比のソースは画面を埋めるようにクロップします |
| Z80リプレイループ | 動作中。パターンとネームの転送は1バイトあたり30サイクルで、Segaが文書化している下限は29です。パレットとネームテーブルの切り替えは、垂直ブランク内のVカウンタガードの中で16サイクルで行います。ビルドゲートと、ビルドしたリプレイをZ80上で実行するテストで保証しています |
| サウンド | PSGでのトーン合成で、フィールドごとに映像の前に書き込みます。`--silent`で省けます。まだ実機では動かしていません |
| 操作 | ループ再生します。ボタン1で最初から再生し、ボタン2で黒い画面に抜けます。ポーズボタン、ゲームギアではスタートボタンで一時停止と再開をします。一時停止中は経過時間と総時間を表示する再生位置バーが出ます。上でサウンドをオフ、オンにします。サウンドは1秒以内に戻ります。ストリームが破損している場合は赤い画面で停止します |
| フィールドレート | NTSCの毎秒59.92フィールドに合わせており、Game Gearも同じレートで動作します。プレイヤーは1フィールドに1チャンクを描画するため、50 HzのPALコンソールでは同じストリームが本来の速度の約6分の5で再生されます。PALコンソールでの確認はまだ行っていません |
| 回帰セット | 種類の異なる6本のクリップを、テスト実行のたびにベイクします |
| 実機での実行 | 未実施です。ここに載っている数値はすべてエミュレーターかリスティングから得たものです |

## 仕組み

### すべてを決める制約

このプレイヤーとNeo Geoの[`neogeo-media-player`](https://github.com/gufranco/neogeo-media-player)は同じファミリーの一員で、2つのマシンは設計が頼る一点で異なります。

Neo Geoは**キャラクターROMに1,048,576個のタイルを常駐**させているため、そのプレイヤーはスプライト制御ブロックにタイル番号を書き込むだけで、実行時にほかの処理をしません。タイル番号がそのままデコード済みの形なので、展開の工程がありません。

Master Systemが扱えるのは**16 KBのVRAMに512パターン**で、1パターン32バイトの512パターンは、ネームテーブルを置く前のVRAMのちょうど全体に当たります。辞書を常駐させることはできません。映像の再生中にROMからページングして読み込む必要があります。

ここから3つの帰結が生まれ、それが設計のすべてです。

| | Neo Geo | Master System |
|---|---|---|
| 支配的な制約 | キャラクターROM | カートリッジのバイト数 |
| フレームごとの処理 | タイル番号を書き込む | パターンを転送し、次にネームテーブルのエントリを書き込む |
| 新しい構成要素 | なし | 何を追い出すかを決めるワーキングセットのポリシー |

映像は全体が一度に切り替わります。ネームテーブルは2つあります。フレームのパターンは画面上のテーブルが使っていないスロットに入り、エントリはもう一方のテーブルに入ります。最後の転送でパレットを書き込み、ある垂直ブランクの先頭でレジスタ2をそのテーブルに切り替えます。フレームの到着中に画面上の表示は何も変わらず、カットで新旧の映像が混ざることもありません。2つ目のテーブルはパターンスロットを64個消費し、映像に残るのは383個です。セルが前のフレームのタイルを保持し続けることはありません。フレームは新しいタイルを、表示中のフレームが空けているスロットの数までマージするので、情報量の多いフレームでは古いパッチが表示されるのではなく、細部が失われます。

### 映像は画面全体を使う

256x192の全ピクセルを使い、周りを囲むものはありません。異なる縦横比のソースはラスターを覆うまで拡大してからクロップするので、16:9の映像は幅の約4分の1を失い、コンソールが描くすべてのピクセルが映像を運びます。

ここでは黒帯は無料ではありません。エンコードされ、パターンスロットを占め、毎フィールド転送されるので、16:9のソースをレターボックスにすると、ワーキングセットの4分の1とフィールドごとの転送量の4分の1を黒の表示に費やすことになります。

`--rows`と`--columns`では今でも小さい映像をビルドでき、ライブラリ側にはそれが必要です。映像は中央に配置され、余った行と列はプレイヤーが黒に保ちます。

### サウンド

サウンドはPSGによるトーン合成で鳴らします。ベイカーはフィールドごとにサウンドトラックを読み、最も強い3つのトーンと高域のノイズを選び、変化したレジスタだけを書き込みます。1フィールドあたり約7回、ROMは毎秒約0.5 KBです。プレイヤーはフィールドの映像の前に、34 Tステート間隔でそれらをPSGへ書き込み、転送ループには手を加えません。会話や密度の高いミックスはトーンになり、旋律のはっきりした音楽が最もよく残ります。`--silent`はサウンドを省き、1フィールドあたり16バイトを映像に戻します。プレイヤーはライン割り込みを一切有効にしないため、アクティブ表示期間を含むフィールド全体が転送ループに使えます。これはまだ実機で動かしていません。

それでも起動時に1回だけPSGに書き込みます。4チャンネルすべてを最大減衰にする書き込みです。コンソールは電源投入時にトーンチャンネルが鳴る状態で起動するため、チップを放置すると映像の間ずっとハム音が鳴ります。

### 先行事例

このコンソール向けの動画の取り組みは4つあります。そのうち3つは1ビットのシルエットアニメーションをエンコードしたもので、大きな平坦領域と2色のパレットによって、カラー映像では到底届かないほどタイルの重複排除が効くため、その数値は目標になりません。

唯一のカラープレイヤーである[gligli's Bad Apple
3D](https://www.smspower.org/Homebrew/BadApple3DFullLength-SMS)が、実質的なベンチマークです。256x192、12.5 fpsで2,724フレーム、3分38秒の映像で4 MBのROMを埋め、その下に10.3 kHzのサンプリング音声を流しています。描画する色は28色で、ハードウェアが同時に表示できる32色の範囲内なので、その上限を超える前例にはなりません。

そのエンコーダーのソースは見つかっていません。GliGliの[tiler](https://github.com/gligli/tiler)リポジトリは後年の別プロジェクトで、TileMotionという汎用ビデオコーデックです。パレットはRGBA8888、リファレンスデコーダーはHTML5 Canvasで、Z80やMaster Systemのターゲットは含まれていません。このファイルの以前の版ではこれをBad Appleのエンコーダーとして挙げていましたが、それは誤りでした。

その成果から1つの技法をこの設計に取り入れています。ブランキング期間に加えてアクティブ表示期間にもVRAMへ書き込むと転送量はおよそ2倍になり、切り替え位置はエンコーダーがオフラインで計算するので、プレイヤーがラスターに応じて分岐することはありません。

### 前提条件

| ツール | バージョン | インストール |

### コードの取得

ベイカーは、デコード、色、映像、キャプチャのコードを[fmv-core-python](https://github.com/gufranco/fmv-core-python)サブモジュールを通じてNeo Geoプレイヤーと共有しているため、サブモジュールを含めてクローンしてください。ダウンロードボタンから得られるソースアーカイブにはサブモジュールが含まれず、動作しません。

```bash
git clone --recurse-submodules https://github.com/gufranco/sms-media-player.git
git submodule update --init   # in a clone made without the flag
```

### カートリッジの作成

任意の動画ファイルからカートリッジをベイクし、続けてビルドします。

```bash
uv --project tools run python -m smsmedia.cartridge input.mp4 --start 300 --duration 5 \
    --preview build/preview.png
make rom
make timing     # VDP write spacing, read out of the assembler's own listing
```

`--preview`は、映像全体から選んだ4フレームをコンソールが描くとおりに、それぞれソースと並べて書き出すので、エミュレーターなしでベイクの出来を判断できます。`.mp4`を指定すると、コンソールが描くすべてのフィールドを動画で書き出します。`build/report.json`のレポートには、自身のタイルの代わりにマージされたタイルを表示したセルである`cells_merged`と、最も多くを失ったフレームである`most_merged_frames`が載るので、結果が悪いときに原因のフレームまでたどれます。`frames_unshown_at_end`は、映像の終わりでデコードされたフレームのうち、空きスロットができる前に時計が過ぎてしまったものの数です。

### 実行

実機では、`build/sms-media-player.sms`をフラッシュカートリッジにコピーします。エミュレーターではウィンドウモードで実行し、フルスクリーンにはしないでください。

```bash
mednafen -video.fs 0 -sound 0 build/sms-media-player.sms
```

### ツールチェーン

すべてのROMビルドはDockerを通り、ホストのツールチェーンを使う経路はありません。[`Dockerfile`](Dockerfile)はSDCCをパッケージのバージョンで、devkitSMSをコミットで、ベースイメージをダイジェストで固定しており、ビルドは呼び出したユーザーとして実行されます。

```bash
make rom        # build/sms-media-player.sms
make analyse    # cppcheck at exhaustive level, must exit 0
make shell      # a shell inside the toolchain image
make clean
```

## 品質

**支配的な制約はROMではなく、フィールドごとの転送量です。** フィールドあたりの転送量を使い切った5秒の映像は62バンクの約3分の1を埋めるだけなので、短いベイクを制限しているのはカートリッジの容量ではありません。制限しているのは各フィールドでVDPに届くバイト数で、割り当てより多くのフィールドを必要とするフレームは遅れて届きます。変更に価値があるのは、その転送量の範囲内で体感画質を上げるときです。

残っている損失の所在を、3つの限界値で特定します。10秒間のアニメのソースで測定しました。

| 限界値 | 誤差 | 許すもの |
|---|---|---|
| 色の下限 | 0.00238 | すべてのピクセルを、コンソールの64色のうち最も近い色にする |
| パレットの下限 | 0.00442 | フィッティングした16エントリのパレット2つを使い、すべてのセルが専用のパターンを持つ |
| 実績 | 0.00565 | 出荷しているワーキングセット |

最初の2つの差は+86%で、これは正確に名指ししておく価値があります。素直な読み方が誤っているからです。これはフレームごとにパレットが2つしかないことのコストではありません。1つのセルが64ピクセルに対して16色しか持てないことのコストです。

この区別が、何を試す価値があるかを決めます。4つの別々の測定がこの点で一致しています。タイル行の帯ごとに専用のパレット2つを与えても0.07%しか改善せず、グレーと高彩度の分割を強制しても効果はなく、8通りの分割からフィッターを初期化しても効果はなく、16色でこの素材を表現できるためセルの96%がすでに1つのパレットを選んでいます。パレットを割り当て直す手法は役に立ちません。どのようなパレット配置でも、1つのセルに17番目の色を与えることはできないからです。

### 指標は暗い色について誤る

Oklabは黒に近い明度を圧縮するため、非常に暗いピクセルでは距離が2つの彩度軸に支配されます。すると、わずかに色の付いた暗いエントリのほうが、ニュートラルなエントリよりも黒に近いピクセルに近いと評価され、そのスコアを追う変更は黒い領域を高彩度の紺色と暗い赤の帯に変えてしまいます。

まさにこの理由で、3つの別々の変更を却下しています。いずれも指標が大きな改善を示した後のことです。知覚的量子化器は36%、パレットへの直接量子化は58%、誤差拡散はぼかした指標で110倍でした。距離を最小化して色を選ぶ変更は、自分自身の目的関数で自分を採点していることになるので、数値を信じる前にレンダリングして暗い領域を見てください。

64色の格子を経由すると最初の2つは防げますが、3つ目は防げません。拡散した誤差が、格子に届く前に暗いニュートラルをニュートラルから外してしまうからです。

### バンディングは指標上は安く見た目には高くつく

帯の中のピクセルはどれも割り当てられた色の近くにあるので、バンディングは二乗誤差ではほとんどコストにならない一方、画面上では最も目立つ欠陥です。この非対称性が上の結果を説明します。誤差拡散はバンディングを消しますがピクセル単位では悪化し、グラデーション専用のパレットは、そうでないパレットとまったく同じスコアになります。

これは打てる手の範囲も限定します。パレットは不足していないので、エントリを割り当て直しても役に立ちません。この映像の中で最悪のケースである回転する惑星で測定すると、内訳は明確です。その領域の誤差はすべて64色の色域によるもので、セルごとに16エントリを選ぶことのコストはゼロ、ワーキングセットが加える誤差もゼロです。直せるのは色数を増やすことであり、ハードウェアにはそれがありません。

そこで量子化器はディザをかけます。64色の格子に丸める前に4x4のBayerしきい値を加え、デフォルトでは最大強度で、`--dither`で指定します。その辺の長さは8ピクセルのタイルを割り切るので、平坦な領域では引き続きタイルが再利用されます。ピクセル単位の指標はどんなディザも損失として採点するので、両側に同じぼかしをかけた後に測った誤差と、レンダリングしたシートの目視の両方で判断します。

| `--dither` | 0 | 0.5 | 0.75 | 1.0 |
|---|---|---|---|---|
| アニメ、ぼかし後の誤差 | 0.0647 | 0.0439 | 0.0325 | 0.0261 |
| ゲーム映像、ぼかし後の誤差 | 0.0695 | 0.0537 | 0.0460 | 0.0437 |

ディザなしでは、淡い空がグレーとピンクの平坦なブロックに丸められます。ディザをかけると、その奥の街並みが戻ってきます。代わりにバイト数がかかります。同じ12秒のアニメで29バンクに対して36バンクですが、5秒のオープニングでは問題になりません。

### 再利用しきい値は固定せず測定する

このしきい値は、セルが新しいパターンを作る代わりに常駐パターンを描くには、そのパターンがどれだけ近ければよいかを決めるもので、誤差とカートリッジのバイト数、つまり再生時間とのトレードオフになります。以前は1本のクリップにフィッティングした定数でしたが、回帰セットで3本のクリップには有利で2本には不利だとわかったため、ノイズ除去と同じようにベイクごとに選ぶようになりました。

この探索を機能させているのは2点です。1つは、しきい値が実際に責任を持つ誤差、つまりコンソールが表示するものと、セルごとにパターンを持った場合に表示するものとの差で採点することです。表示される誤差の合計はパレット量子化に支配されており、映像が壊れてもほとんど動かないからです。もう1つは、前のフレームを表示したままのセルが0.5%を超える候補を除外することです。そのにじみは誤差の数値には現れませんが、動きの中でははっきり見えるからです。

探索の公正さを保つルールが2つあります。ノイズ除去は、リプレイした映像を、ノイズ除去なしでデコードした1つの基準に対して、両側に同じぼかしをかけて採点します。自分自身のフィルター済み入力に対して採点すると、常に最も強いフィルターが勝っていました。また、最良から5%以内のスコアは同点とし、最も安い候補を選びます。1、2%の差はノイズであり、高くつく設定はフレームの空きスロットより多くのタイルを作ってしまうからです。

`--reuse <value>`で今でも1つの値を強制できます。過去の曲線を、32x18で1つの20秒区間について測定したものです。

| 再利用 | 誤差 | フレームあたりのバイト数 | 62バンクに入る秒数 |
|---|---|---|---|
| 0.016 | 0.00863 | 1,254 | 67.5 |
| 0.012 | 0.00789 | 1,660 | 51.0 |
| 0.008 | 0.00706 | 2,279 | 37.2 |
| 0.006 | 0.00653 | 2,664 | 31.8 |
| 0.004 | 0.00614 | 3,041 | 27.8 |
| 0.001 | 0.00564 | 4,005 | 21.1 |

1つの20秒区間での測定です。曲線の形は成り立ちますが、絶対値は成り立ちません。同じ映像のより動きの多い部分ではフレームあたりのコストがほぼ2倍になるので、最後の列は計画に使う再生時間としてではなく、行どうしの比として読んでください。

ここには、映像を収めるために短くする処理はありません。ベイカーは収まる再生時間を報告して停止します。

### 測定して却下したもの

以下はいずれも、実装して測定した後に無効にしたものです。呼び出し元がなくなったコードはその後削除しており、測定結果が記録として残っています。

- **ライン割り込みによるパレットの帯**：0.07%です。タイル行の帯ごとに両方のパレットをフィッティングし直して再測定しました。1帯から18帯、つまり色スロットを32から576にしても、誤差は0.00688から0.00687にしか変わりませんでした。パレットを増やしてもセルの色は増えず、限界はセルにあります
- **知覚的な最近傍色の量子化器**：指標は36%改善しましたが、映像は明らかに悪化しました。Oklabによる選択をOklabの指標で判断するのは循環論法です
- **タイルの反転**：0.3%悪化しました。完全な反転になっているセルは0.5%しかありません
- **パレットエントリ間の組織的ディザ**：ピクセルの0.09%しか動かず、どちらの指標も変わりませんでした。この手法はピクセルに最も近い2つのエントリの間で選択しますが、色の帯の内側ではどのピクセルもほぼ正確に1つのエントリ上にあるため、帯の境界でしか働かず、帯を崩せません。代わりに量子化の前に摂動を加える方式を`--dither`で出荷しています
- **明度に応じたディザの減衰**：一度出荷して誤りでした。1段階は255のうち85なので黒の上では目立つという主張で、実際に星空の上にクロスハッチが現れていました。そのクロスハッチは背景の星雲でした。ソースでは暗い領域の62.3%が黒ではなく平均2.70で、減衰ありのビルドは0.5%を平均0.15で描き、減衰を外すと6.2%、平均1.75に戻りました。組織的しきい値は真のゼロを持ち上げられないので前提が誤っており、暗い領域に描かれるものはどれも捏造ではありません。誤りのコストは、誤差9.6%、フレームあたり6バイト、1バンクで、すべて悪い方向でした
- **明度ゲートより上での知覚的な最近傍色**：指標では全体で5.1%、明るいピクセルで28%の改善でしたが、レンダリングすると惑星にマゼンタの斑点が出ました。ゲートは、ゲートなし版を沈めた暗い色相の失敗を防ぐためのもので、実際に防いでいますが、中程度の明度で同じ彩度ノイズが再び現れます。Oklabの選択をOklabの指標で判断する循環は、ゲートをどこに置いても残ります
- **64色の格子を飛ばしてパレットへ直接量子化**：指標は58%改善しましたが、映像は明らかに悪化しました。Oklabは黒に近い明度を圧縮するため、暗いピクセルでは距離が彩度軸に支配され、わずかに青いエントリのほうがニュートラルなエントリより黒に近いピクセルに近いと評価されます。暗い周囲全体が紺色と暗い赤の帯になりました。冗長に見える格子の経由こそが、黒に近い色をニュートラルに保っています
- **Floyd-Steinberg誤差拡散**：バンディングは消えますが、コストを賄えません。フレームあたりの異なるタイル数が204から434になり、7,160バイトの転送量に対してパターンデータは13,888バイトとなるので、ROMを考える前に帯域を1.9倍超過します。さらに220のマージ上限を超えるため、エンコーダーがディザを再びクラスタリングで消してしまいます。暗い周囲に赤と青の斑点も出ます。これは3度目の黒に近い色の問題で、格子を経由しても防げません。拡散した誤差が量子化の前に暗いニュートラルをニュートラルから外してしまうからです
- **フレームごとのパレットの再割り当て**：改善なし。セルの96%がパレット0を選び、16エントリのうち14がもう一方のパレットと重複しています。無駄に見えますがそうではありません。この映像に必要な色は約16色なので、1つのパレットで足り、2つ目は本当に余っています。グレーと高彩度の分割を強制し、一方のパレットが16エントリすべてをグラデーションに使うようにしても、誤差は0.00383のまま変わらず、フレームあたりのタイル数は130から185に増えました
- **フレームあたりのバイト数を稼ぐための8 fpsへの低下**：逆効果です。12 fpsの2,205バイトに対してフレームあたり4,301バイトになりました。フレームが少ないほどフレーム間の変化が大きく、再利用できるものが減るからです。50バンクに対して78バンクでした
- **448セルより広い映像**：指標では良く、画面では悪く、誤っているのは指標のほうです。VRAMには448パターンが入るので、32x18の映像では576セルがそれを共有することになり、形状がフレーム内の別の場所からタイルを借ります。28x16の映像ならセル数とスロット数がちょうど一致し、0.00547に対して0.00478、フレームあたり826バイトに対して713バイトです。ただしピクセル数も22%少なくなります。誤差は各解像度自身の縮小画像に対してピクセル単位で計上されるので、小さい映像は誤りうる部分が少ないことで有利になります。実際の256x192の画面に同じ倍率で合成すると、大きいほうが惑星の表面をはっきり多く見せます。576セルを維持し、その後置き換えられました。現在の映像は768セルでラスターを埋めており、同じ議論を反対側から決着させています
- **ブロック感の対策としての細かい再利用しきい値**：誤差は改善しますが、見た目には何も変わりません。細部の保持率は再利用0.012で84.5%、0.001でも84.5%で、カートリッジは13バンクから51バンクになります。粗さを決めているのは16色を持つ8x8ピクセルのセル格子であり、どのしきい値もそこには届きません
- **量子化器の前段での鋭いスケーラー、または弱いノイズ除去**：ディザ導入前に32x18で測定したもので、その後ベイクごとのノイズ除去探索に置き換えられました。当時は効果がありませんでした。各変種自身の縮小画像ではなく固定の1つのlanczos基準に対して採点すると、area、lanczos、bicubic、spline、bilinearは0.00502から0.00507の範囲、ノイズ除去0から4は0.00501から0.00503の範囲でした。量子化器が完全に支配しているため、入力フィルターは無関係です
- **220を超えるマージ上限**：上限が効かない576セルでは出力がビット単位で同一でした。768セルでは強く効きます。200では回帰セット全体で675セルが前のフレームを表示したままになり、224では2,401セルになったため、上限を160に、2つ目のネームテーブルが64スロットを取ってからは130にしました。それらの古いセルは、空きスロットが見つからなかったタイルを捨てたことで生じていました。フレームが空きスロットの数までマージするようになってからは、上限が古いセルを生むことはなくなり、200になりました。そこでは空きスロットのほうが先に制約になります。ある映像サイズで成り立つ知見は、エンコーダーについての知見ではありません

- **線形光でのディザ**：ぼかした指標はそれぞれ、自身の色空間で行ったディザを有利に評価します。アニメで、Oklabでぼかすと0.0408に対して0.0260、線形光でぼかすと0.0302に対して0.0370でした。レンダリングするとアニメの木がオレンジがかった赤になり、空にパッチが出ます。ゲーム映像では結果がまちまちです。無効のままです

### 採用したもの

- **フレーム全体の書き込み、旧来の26サイクルループで測定**：9.10から20.35 fps、単独で最大の改善
- **常駐タイルの再利用**：4.07から15.77 fps、誤差も低下
- **実写ではなくアニメのソース**：誤差が44%低下
- **ベイクごとに測定するノイズ除去**：最大8%、これに勝つ定数はありません
- **前フレームのパレットの維持**：維持したパレットの誤差が新規フィッティングの誤差を30%を超えて上回るときだけ、新規フィッティングで置き換えます。ゲーム映像では、ぼかし後の誤差が0.0397から0.0347、状態の悪いセルが418から100、40バンクから24バンクになりました。アニメでは0.0258から0.0249、37バンクから26バンクです。再フィッティングすると常駐タイルがすべて色付け直されるため、静止した領域が変化し、再利用する価値のある常駐タイルが減っていました
- **パレットごとに限定したタイルのマージ**：マージされたセルは代わりのタイルを自身のパレットで描きますが、以前のマージはもう一方のパレットのセルから取ったタイルを渡しており、そのインデックスが誤った色で描かれていました。これが忙しい場面での迷子のタイルの正体です。ひどく誤ったセルは、群衆の映像で707から1、ゲーム映像で340から5、アニメで8から0に減りました
- **ひどく誤ったセルを残さない**：セルのソースに対するOklab距離の平均が0.25を超えると、そのセルはひどく誤っているとみなします。マージ後、代わりのタイルでそれを超えるセルには、悪いものから順に専用のタイルを与え、それでもそうしたセルが残るパレットはもう一方からスロットを借ります。各ステップは件数が減る場合にのみ採用します。ここにあるすべての映像、つまりゲーム、アニメ、群衆、街、鳥、3Dの5秒区間12個にわたって、件数はゼロです。2つの誤差は加算されるため、セル自身のタイルに対してではなくソースに対して測定しています
- **より近い場合に、マージされたセルが画面上の既存タイルを使う**：画面上のフレームがまだ使っているタイルはこのフレームでは上書きできないので、それを指すのはコストがかかりません。マージされたセルは、ピクセル単位でも同じぼかしの後でも近い場合に、そのタイルへ切り替えます。ゲーム映像ではフレームの最悪10%が0.0294から0.0284、ストリームが19バンクから17バンクになり、群衆の映像では最悪フレームが0.0540から0.0494、27バンクから21バンクになりました。ぼかした表示だけで切り替えを許すと、状態の悪いセルが22に対して363に増え、ゲームの1フレームに誤ったタイルの帯ができました
- **フレームごとの誤差の90パーセンタイルによる再利用の選択**：平均では、カットの1フレームをにじませるしきい値が勝ってしまいました。アニメの最悪フレームは0.0412から0.0297に戻りました
- **リプレイした映像をノイズ除去なしの基準に対して採点し、ほぼ同点なら安い設定を選ぶノイズ除去**：パレットの持ち越しによって、両方の探索が1から2%差で勝つ設定に流れ、2倍のセルをマージしていました。アニメでは最悪フレームが0.0420から0.0303に戻り、状態の悪いセルが142から8に減りました。ゲーム映像では、フェードの終わりで壊れていたHUDが直りました
- **各セルのぼかした表示でのタイルのマージ**：ゲーム映像で、39バンク中1バンクのコストでぼかし後の誤差が0.0412から0.0394になり、アニメは同等でした。ディザがあると、似て見える2つのタイルでもピクセルの大半が異なることがあり、ピクセル単位の距離ではディザを誤ったタイルにマージしていました

ノイズ除去を固定せずに測定するのは、適切な強度が映像の性質によって決まるからです。1本の映像の15秒区間3つが、それぞれ異なる3つの強度を選び、最良と最悪の選択の差は8%でした。

| リプレイオラクル | ベイカーのストリームモデルが、エンコーダーの意図した映像を小数点以下5桁まで再現すること |
| mednafenのキャプチャ | mednafenからキャプチャしたフレームがリプレイオラクルとピクセル単位で一致し、オラクルが画面を代表できること |
| `make timing` | コンパイル済みプレイヤーのすべてのVDP書き込みペアが29 Tステート、ガードされた垂直ブランク内のコピーでは16 Tステートを満たすこと。すべてのリスティングを1つのプログラムとしてたどります |
| `test_osd_on_z80.py` | ビルドした一時停止オーバーレイをVDPモデル相手にZ80上で実行し、経過時間と総時間、バー、そのパレットがスプライトの読む場所に書かれること |
| `test_replay_on_z80.py` | ビルドしたリプレイを、Vカウンタを選んだラインに固定してZ80上で実行し、パレットのバイトや切り替えが期間外にVDPへ届かないこと |
| 回帰セット | 種類の異なる6本の映像がテスト実行のたびにベイクされ、それぞれ測定済みの誤差とバンク数の予算に収まること |
| EverdriveのGame Gear | 同じクロックの同じVDPコアでの書き込みタイミング。色をリマップし、中央の160x144しか表示しないので、色も画面の端も確定させません |

VDPの書き込み間隔を強制するエミュレーターはないため、転送ループへの変更は、手元の数値がどれほど良く見えても、実機で実行するまでは未検証です。

## 開発

pre-commitフックを一度インストールしてください。コミットのたびに、フォーマッター、リンター、型チェッカー、カバレッジ下限付きのテストスイートを実行し、ステージされたパスがプレイヤーに影響しうる場合は、ROMのビルド、静的解析、タイミングゲート、Z80リプレイも実行します。

```bash
make hooks
```

```bash
# フォーマット
uv --project tools run ruff format tools/

# リントゲート
uv --project tools run ruff check tools/

# 型ゲート
uv --project tools run mypy tools/smsmedia tools/scripts

# テスト、カバレッジ下限95%
uv --project tools run python -m pytest tools/tests --cov=smsmedia --cov=tools/scripts --cov-config=tools/pyproject.toml --cov-fail-under=95

# 回帰用の映像の取得と検証
uv --project tools run python tools/scripts/fetch_clips.py

# 固定したイメージ内でのプレイヤーのゲート
make rom`、`make analyse`、`make timing
```

回帰セットは、意図的に種類を変えた6本のクリップをベイクします。これらはリポジトリに含まれておらず、再配布できるものでもないため、マニフェストにはその識別情報を記録し、上のスクリプトで取得と検証を行います。それらがない場合はコミット済みの合成クリップだけが実行され、ゲートは大幅に弱くなります。クレジットとライセンスはすべて[`tools/clips.manifest.json`](tools/clips.manifest.json)にあります。

## よくある質問

<details>
<summary><strong>なぜタイルをROMに格納せずにページングするのですか？</strong></summary>
<br>

Master SystemはVRAMからしか描画できず、VRAMには512パターンしか入りません。映像には数千のパターンが必要なので、それらはカートリッジに置かれ、プレイヤーは各フレームの新しいパターンを、画面が表示していないスロットにコピーします。

</details>

<details>
<summary><strong>Game Gearで動きますか？</strong></summary>
<br>

Everdriveを挿したGame GearはMaster SystemのROMを実行でき、ここではそれで書き込みタイミングを確認しています。Master Systemモードでは映像の中央160x144しか表示せず、パレットもリマップするので、映像全体を表示するのはMaster Systemの役割です。

</details>

<details>
<summary><strong>PALコンソールで再生できますか？</strong></summary>
<br>

NTSCの毎秒59.92フィールドに合わせています。プレイヤーは1フィールドに1チャンクを描画するため、50 Hzのコンソールでは同じストリームが本来の速度の約6分の5で再生されます。PALコンソールでの確認はまだ行っていません。

</details>

<details>
<summary><strong>なぜ無音なのですか？</strong></summary>
<br>

現在は転送ループがフィールドのすべてのサイクルを使っており、PSGにはサンプル再生用のチャンネルがないため、サウンドには映像が今使っているZ80の時間が必要になります。サウンドはファミリーが定める要件であり、予定しています。

</details>

## ファミリー

このプレイヤーは、本来フルモーションビデオを表示するよう作られていないコンソールでそれを再生するファミリーの一員です。メンバーは1つの標準[FAMILY.md](FAMILY.md)を共有し、ハードウェアが強制しないベイカーのコードはすべてコアに1つだけ置かれています。

| メンバー | 内容 |
|:--|:--|
| [neogeo-media-player](https://github.com/gufranco/neogeo-media-player) | Neo Geo AESまたはMVSでのサウンド付きフルスクリーン映像と、別のゲームの中で映像を再生するライブラリ |
| [sms-media-player](https://github.com/gufranco/sms-media-player) | このリポジトリ |
| [fmv-core-python](https://github.com/gufranco/fmv-core-python) | 各プレイヤーが共有するベイカーと測定のコード |
