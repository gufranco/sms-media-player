## 這是甚麼

一個把任何影片檔案轉成 Master System 或 Game Gear 卡帶的烘焙器，以及一個在原裝遊戲機上全螢幕播放的 Z80 播放器。每部遊戲機都有自己的卡帶，按它自己的螢幕、顏色及聲音建置。烘焙器在宿主電腦上執行；播放器及每次 ROM 建置都在一個版本固定的 Docker 映像內執行。

### 問題

Master System 除了圖塊顯示之外，沒有任何視訊硬件。它從 16 KB 的 VRAM 繪製 8x8 的圖案，VRAM 只容得下 512 個，而一部影片需要數千個。Z80 以 3.58 MHz 運行，在畫面繪製期間，VDP 接收字節的速度不能快過每 29 個 T 狀態一個。遊戲機上沒有時間解碼任何東西，連搬運資料的時間也很緊絀。

### 解決方法

遊戲機上不作任何解碼。烘焙器把影片變成一串圖案上傳及名稱表寫入，並安排好次序，令每場的份額都落在 VDP 容許的時間之內。播放器每場複製一個資料塊，並在垂直消隱期整體切換畫面，因此永遠不會見到畫了一半的幀。

### 現況

整條流程都能運作：預處理、編碼器、記憶庫打包、Z80 播放器及操控。

| 部件 | 狀態 |

## 運作原理

### 決定一切的限制

本播放器與 Neo Geo 的 [`neogeo-media-player`](https://github.com/gufranco/neogeo-media-player) 同屬一個家族，而兩部機器正好在設計所依賴的那一點上不同。

Neo Geo 有 **1,048,576 個圖塊常駐於字元 ROM**，因此其播放器只需把圖塊編號寫入精靈控制區塊，執行時不做其他事。圖塊編號本身就是解碼後的形式，所以沒有解壓步驟。

Master System 在 **16 KB 的 VRAM 中可定址 512 個圖案**，而 512 個每個 32 字節的圖案，在放置名稱表之前恰好佔滿整個 VRAM。字典無法常駐，必須在影片播放期間從 ROM 換入。

由此得出三個結果，而它們就是整個設計。

| | Neo Geo | Master System |
|---|---|---|
| 約束所在 | 字元 ROM | 卡帶字節 |
| 每幀工作 | 寫入圖塊編號 | 上載圖案，然後寫入名稱表項目 |
| 新增部件 | 無 | 一個決定逐出哪些內容的工作集策略 |

畫面整幅切換。名稱表有兩個：一幀的圖案寫入螢幕上那個表沒有使用的槽位，其項目寫入另一個表，而它的最後一段寫入會寫入調色盤，並在某個垂直消隱開始時把暫存器 2 切換至該表。一幀到達期間，螢幕上沒有任何變化，切鏡時也不會出現新舊畫面混雜。第二個表佔用 64 個圖案槽位，留給影片 383 個。一個格子永不沿用較早一幀的圖塊：一幀會把新圖塊合併至顯示中那一幀所空出的槽位數目之內，因此繁忙的幀會損失細節，而不會顯示過時的色塊。

### 畫面就是整個螢幕

全部 256 乘 192 個像素，四周沒有任何框邊。其他比例的來源會縮放至覆蓋整個光柵後再裁切，因此 16:9 的影片會失去約四分之一寬度，而遊戲機繪出的每個像素都是影片內容。

黑邊在這裏並非免費。它們會被編碼、佔用圖案槽位，並且每場都要傳送，所以為 16:9 來源加上黑邊，會花掉四分之一的工作集及四分之一的每場預算來傳送黑色。

`--rows` 及 `--columns` 仍可建置較小的畫面，這正是程式庫部分所需。畫面置中，剩下的行與列由播放器保持黑色。

### 聲音

聲音由 PSG 以音調合成發出。烘焙器每場讀取一次音軌，選出最強的三個音符，略過已選音符的泛音，讓每個持續的音符留在自己的聲道上，按前後 8 秒內場景的響度設定音量，令安靜的段落仍然聽得見，再加上高頻噪音，只寫入有變化的暫存器：在回歸測試影片上每場 3 至 6 位元組，ROM 每秒少於 0.4 KB。播放器在每場畫面之前把它們寫入 PSG，相隔 34 個 T 狀態，傳輸迴圈不受影響。對白及密集的混音會變成音調；旋律清晰的音樂保留得最好。`--silent` 會略去聲音，把每場的 15 位元組還給畫面。播放器從不啟用行中斷，因此整個場，包括有效顯示期間，都留給傳輸迴圈。它已在 Master System 及 Game Gear 上播放過。

它仍會在開機時寫入 PSG 一次：把全部四個聲道設為完全衰減。遊戲機開機時音調聲道是有聲的，若不理會該晶片，整部影片都會伴隨嗡嗡聲。

### 前人成果

這部遊戲機已有四個影片方案。其中三個編碼的是 1 位元剪影動畫，大片平坦區域加上雙色調色盤，令圖塊去重的效果遠超彩色影片所能達到，因此它們的數字不是目標。

唯一的彩色播放器，[gligli 的 Bad Apple 3D](https://www.smspower.org/Homebrew/BadApple3DFullLength-SMS)，是公允的基準：256x192、12.5 fps、2,724 幀，三分三十八秒填滿一個 4 MB ROM，底下還有 10.3 kHz 的取樣音訊。它繪出 28 種不同顏色，在硬件可同時顯示的 32 種之內，所以並不構成超出此數的先例。

其編碼器原始碼尚未找到。GliGli 的 [tiler](https://github.com/gligli/tiler) 儲存庫是較後期的另一個項目，是一個名為 TileMotion 的通用影片編解碼器，其調色盤為 RGBA8888，參考解碼器為 HTML5 Canvas，當中沒有任何 Z80 或 Master System 目標。本檔案較早的版本曾把它引述為 Bad Apple 的編碼器，那是錯的。

該作品有一項技術延續到本設計。除消隱期外，亦在有效顯示期間寫入 VRAM，大約可令預算加倍，而切換點由編碼器離線計算，因此播放器從不需要按光柵位置分支。

| 資源 | 上限 | 後果 |
|---|---|---|

| 卡帶 | 經 Sega mapper 的 64 個 16 KB 記憶庫，其中兩個是程式碼 | 烘焙器目前的上限是 62 個影片記憶庫 |
| 工作 RAM | 8 KB，位於 `$C000`，鏡像於 `$E000` | mapper 暫存器位於鏡像區 |

### 取得程式碼

烘焙器透過 [fmv-core-python](https://github.com/gufranco/fmv-core-python) 子模組，與 Neo Geo 播放器共用解碼、顏色、影片及擷取程式碼，因此複製時要連同子模組。從下載按鈕取得的原始碼壓縮檔無法包含子模組，亦無法運行。

```bash
git clone --recurse-submodules https://github.com/gufranco/smsgg-media-player.git
git submodule update --init   # in a clone made without the flag
```

### 製作卡帶

一個指令便可從任何影片檔案烘焙影片並建置 ROM。`--bake-only` 會在烘焙之後、建置 ROM 之前停止：

```bash
uv --project tools run python -m smsggmedia.cartridge input.mp4 --start 300 --duration 5 \
    --preview build/preview.png
make timing     # VDP write spacing, read out of the assembler's own listing
```

`--preview` 會從影片各處取四幀，按遊戲機將繪出的樣子寫出，每幀旁邊附上其來源，因此無需模擬器亦可評估一次烘焙。指定 `.mp4` 時，則輸出遊戲機繪出的每一場組成的影片。`build/report.json` 中的報告列出 `cells_merged`，即顯示合併圖塊而非自身圖塊的格子，以及 `most_merged_frames`，即損失最多的幀，因此結果欠佳時可追溯至導致問題的幀。`frames_unshown_at_end` 計算影片結尾有多少已解碼的幀，在有空槽位容納它們之前，時鐘已越過它們。

### 運行

在硬件上，把 `build/smsggmedia.sms`，或 Game Gear 用的 `build/smsggmedia.gg`，複製到快閃卡帶。在模擬器下，以視窗模式執行，切勿全螢幕：

```bash
mednafen -video.fs 0 -sound 0 build/smsggmedia.sms
```

### 工具鏈

每次 ROM 建置都經由 Docker，沒有宿主電腦工具鏈路徑。[`Dockerfile`](Dockerfile) 以套件版本固定 SDCC、以 commit 及封存檔的 SHA-256 固定 devkitSMS、以 digest 固定基礎映像，而建置以呼叫者的使用者身分執行。


### 在你自己的遊戲中播放影片

`--bundle DIR` 會寫出一個可直接嵌入你自己的 devkitSMS 遊戲的資料夾：原始碼形式的播放器程式庫、影片、`fmv.mk` 片段，以及按你烘焙的影片寫成的指南。[`examples/cutscene/`](examples/cutscene) 是用它建置的遊戲，執行 `make example` 即可。

## 質素

**約束所在是每場傳輸量，而不是 ROM。** 以完整的每場預算計，五秒約填滿 62 個記憶庫的三分之一，因此卡帶空間並非短片烘焙的限制。限制在於每場有多少字節送達 VDP，而所需場數多於其時段的幀就會遲到。一項改動若能在該傳輸量之內提升觀感質素，才值得採用。

三個界限指出剩餘損失所在，量度對象為十秒卡通來源：

| 界限 | 誤差 | 所容許的 |
|---|---|---|
| 顏色下限 | 0.00238 | 每個像素取 64 種遊戲機顏色中最接近的一種 |
| 調色盤下限 | 0.00442 | 兩個擬合出的 16 色調色盤，每個格子有自己的圖案 |
| 實際達到 | 0.00565 | 已發佈的工作集 |

頭兩者之間的差距是 +86%，值得準確說明，因為顯而易見的解讀是錯的。它不是每幀只有兩個調色盤的代價，而是一個格子的 64 個像素只有 16 種顏色的代價。

這個區別決定了甚麼值得嘗試。現時有四項獨立量度一致支持這點：為每一帶圖塊行各設兩個調色盤只換來 0.07%，強制作灰色對飽和色的分割毫無得益，以八種分割作擬合器的起點毫無得益，而 96% 的格子本已只選用一個調色盤，因為 16 種顏色已足以應付這類素材。任何重新分配調色盤的做法都幫不上忙，因為沒有任何調色盤安排能給單一格子第 17 種顏色。

### 如何評判畫面

#### 指標在暗色上會說謊

Oklab 在接近黑色處壓縮亮度，因此對很暗的像素而言，距離主要由兩條色度軸決定。於是一個略帶色調的暗色項目，會比中性項目更接近一個近黑像素，而追逐這個分數的改動會把黑色區域變成飽和的海軍藍及暗紅色帶。

已有三項不同改動正因此被否決，每一項都曾被某個指標判為大勝：感知量化器 36%、直接調色盤量化 58%，以及在模糊指標上 110x 的誤差擴散。任何以最小化距離來選色的改動，都是以自己的目標函數為自己評分，因此在相信數字之前，先渲染出來看看暗部。

經由 64 色網格處理可防範前兩者，但防不了第三者，因為擴散的誤差在到達網格之前，已把暗的中性色推離中性。

#### 色帶對指標來說代價低，看起來卻代價高

色帶中每個像素都接近它所分配的顏色，因此色帶在平方誤差上幾乎沒有代價，卻是螢幕上最明顯的瑕疵。這種不對稱解釋了上述結果：誤差擴散消除了色帶，但逐像素看更差；而專為漸變而設的調色盤，與沒有這樣做的調色盤得分完全相同。

這也限定了可行的範圍。調色盤並不缺項，所以重新分配項目幫不上忙。以一個旋轉中的行星量度，這是這批片段中最差的情況，結果毫不含糊：64 色色域佔該區域的全部誤差，每格 16 項的選擇代價為零，工作集亦增加零。能解決問題的是更多顏色，而硬件沒有。

所以量化器會抖動。在捨入至 64 色網格之前加上 4x4 Bayer 閾值，預設為全強度，經 `--dither` 設定。其邊長可整除 8 像素的圖塊，所以平坦區域仍能重用圖塊。逐像素指標會把任何抖動計為損失，因此它以兩邊經相同模糊後量度的誤差，以及親眼看渲染出的對照表來評判：

| `--dither` | 0 | 0.5 | 0.75 | 1.0 |
|---|---|---|---|---|
| 卡通，模糊後誤差 | 0.0647 | 0.0439 | 0.0325 | 0.0261 |
| 遊戲片段，模糊後誤差 | 0.0695 | 0.0537 | 0.0460 | 0.0437 |

不抖動時，淡色天空會捨入成一塊塊平坦的灰色及粉紅色；抖動後，天空後面的城市重現。代價是字節：同樣十二秒的卡通需 36 個記憶庫，對比 29 個。

#### 重用閾值是量度出來的，不是設定的

它決定一個常駐圖案要多接近，格子才會改用它而不是新造一個，並在誤差與卡帶字節之間取捨，因而亦在誤差與播放時長之間取捨。它原本是一個按單一片段擬合的常數，直至回歸測試集顯示它對三段片段有幫助、對兩段有害，所以現時它按每次烘焙選定，與降噪的做法一樣。

有兩點令這個搜尋行得通。其一，它以閾值真正負責的誤差評分，即遊戲機所顯示的與每格一個圖案時應顯示的之間的差距，因為顯示總誤差由調色盤量化主導，即使畫面被毀也幾乎不動。其二，若某個候選值令超過 0.5% 的格子顯示上一幀，它就會從候選池中剔除，因為這種拖影在誤差數字上看不見，在動態畫面中卻很明顯。

有兩條規則令搜尋保持誠實。降噪以重播出的畫面評分，對比一個未經降噪解碼的參照，兩邊同樣模糊；若以自身濾波後的輸入評分，最強的濾波總會勝出。另外，與最佳值相差 5% 以內的分數視為打和，由最便宜的候選值勝出，因為一兩個百分點只是雜訊，而較昂貴的設定所新造的圖塊，多於一幀可用的空槽位。

`--reuse <value>` 仍可強制使用某個值。歷史曲線，於單一個二十秒時段以 32x18 量度：

| reuse | 誤差 | 每幀字節 | 62 個記憶庫可容納秒數 |
|---|---|---|---|
| 0.016 | 0.00863 | 1,254 | 67.5 |
| 0.012 | 0.00789 | 1,660 | 51.0 |
| 0.008 | 0.00706 | 2,279 | 37.2 |
| 0.006 | 0.00653 | 2,664 | 31.8 |
| 0.004 | 0.00614 | 3,041 | 27.8 |
| 0.001 | 0.00564 | 4,005 | 21.1 |

於單一個二十秒時段量度。曲線形狀成立，絕對數字則不然：同一部影片中較繁忙的段落，每幀代價接近兩倍，因此最後一欄應視為各行之間的比例，而不是可據以規劃的播放時長。

這裏沒有任何機制會為遷就容量而縮短影片。烘焙器只報告可容納的播放時長，然後停止。

### 量度後否決的方案

以下每一項都曾實作並量度，然後才關閉。已沒有呼叫者的程式碼其後已刪除；量度結果就是紀錄。

- **經行中斷實現的調色盤分帶**：0.07%。以在每一帶圖塊行內重新擬合兩個調色盤的方式重新量度：由一帶增至十八帶，即由 32 個顏色槽增至 576 個，誤差由 0.00688 變為 0.00687。額外的調色盤不會給格子額外的顏色，而限制正在於格子
- **感知最近色量化器**：指標好 36%，畫面明顯更差。以 Oklab 指標評判 Oklab 的選擇是循環論證
- **圖塊鏡像**：差 0.3%。只有 0.5% 的格子是完全鏡像
- **在調色盤項目之間作有序抖動**：只移動 0.09% 的像素，兩個指標均紋風不動。它在像素最接近的兩個項目之間選擇，而在色帶內每個像素幾乎正好落在某一項目上，所以只會在色帶邊緣觸發，無法打散色帶。改為在量化前加擾動才是實際採用的做法，即 `--dither`。Game Gear 有 4096 種顏色，大部分像素落在 32 個項目之間，所以同樣的混合會在該抖動之後執行，正是它把抖動帶到螢幕上，兩部遊戲機走同一條路徑
- **按亮度減弱抖動**：曾經發佈，而且是錯的。當時的論點是一級等於 255 中的 85，因此在黑色上很刺眼，而星空上確實出現了交叉紋。那交叉紋其實是背景星雲：來源的暗區有 62.3% 非黑，平均值 2.70；減弱後的建置只繪出 0.5%，平均值 0.15；移除減弱後恢復至 6.2%，平均值 1.75。前提是錯的，因為有序閾值無法提升真正的零，所以它在暗區所繪的一切都不是無中生有。這個錯誤的代價：誤差 9.6%、每幀六個字節及一個記憶庫，全部朝錯誤方向
- **亮度閘門以上的感知最近色**：指標顯示整體好 5.1%，有光像素好 28%；渲染出來，行星佈滿洋紅色斑點。閘門原意是阻擋令未設閘門版本失敗的暗部色相問題，它也做到了，但同樣的色度雜訊在中等亮度重新出現。不論閘門放在哪裏，以 Oklab 指標評判 Oklab 選擇始終是循環論證
- **直接量化至調色盤，跳過 64 色網格**：指標好 58%，畫面明顯更差。Oklab 在接近黑色處壓縮亮度，所以對暗像素而言，距離主要由色度軸決定，一個略帶藍色的項目會比中性項目更接近近黑像素。整個暗色周邊變成海軍藍及暗紅色帶。看似多餘的網格中轉，正是保持近黑色中性的關鍵
- **Floyd-Steinberg 誤差擴散**：能打散色帶，但負擔不起。每幀不同圖塊由 204 增至 434，即 13,888 字節的圖案數據，而傳輸預算是 7,160 字節，因此未計 ROM 已超出頻寬 1.9x；它亦超過 220 的合併上限，編碼器會再次把抖動聚類掉。它還在暗色周邊灑上紅藍斑點，這是第三次遇上近黑問題，而經由網格處理無法防止，因為擴散的誤差在量化前已把暗的中性色推離中性
- **每幀重新分配調色盤**：沒有得益。96% 的格子選用調色盤 0，16 個項目中有 14 個與另一調色盤重複，看似浪費，其實不然：這批片段約需 16 種不同顏色，所以一個調色盤已足夠，第二個確實是多餘的。強制作灰色對飽和色的分割，令一個調色盤把全部 16 項用於漸變，誤差維持在 0.00383 不變，而每幀圖塊由 130 增至 185
- **降至 8 fps 以換取每幀字節**：適得其反。每幀 4,301 字節，對比 12 fps 時的 2,205 字節，因為幀數越少，幀與幀之間的變化越大，可重用的越少。78 個記憶庫對比 50 個
- **寬於 448 個格子的畫面**：指標上較好，螢幕上較差，而出錯的是指標。VRAM 可容納 448 個圖案，因此 32x18 的畫面要 576 個格子共用它們，形狀要從幀內其他位置借用圖塊。28x16 的畫面令格子與槽位數目恰好相符，量得 0.00478 對比 0.00547，每幀 713 字節對比 826。它的像素也少 22%。誤差是按每種幾何各自的縮小版本逐像素計算，所以較小的畫面因較少東西可出錯而獲得獎勵；以相同比例合成到真正的 256x192 螢幕上時，較大的那個明顯顯示更多行星表面。當時保留 576 個格子，其後已被取代：畫面現在以 768 個格子填滿光柵，從另一方向解決了同一爭論
- **以較細的重用閾值治理方塊感**：換來誤差改善，但看不出任何分別。重用 0.012 時細節保留率為 84.5%，0.001 時亦是 84.5%，而卡帶由 13 個記憶庫增至 51 個。粗糙感由格子網格決定，即 8x8 像素容納 16 種顏色，任何閾值都觸及不到
- **在量化器之前用較銳利的縮放器或較少降噪**：在抖動之前以 32x18 量度，其後已被每次烘焙的降噪搜尋取代。當時沒有效果。以單一固定的 lanczos 參照評分，而非各變體自身的縮小版本，area、lanczos、bicubic、spline 及 bilinear 介乎 0.00502 至 0.00507，降噪由 0 至 4 介乎 0.00501 至 0.00503。量化器的主導程度之高，令輸入濾波無關痛癢
- **高於 220 的合併上限**：在 576 個格子時輸出逐位元相同，因為上限在那裏從不起約束作用。在 768 時則嚴重受約束：200 令回歸測試集中 675 個格子顯示上一幀，224 則令 2,401 個如此，所以上限改為 160，第二個名稱表佔去 64 個槽位後再改為 130。那些過時的格子來自丟棄找不到空槽位的圖塊；一旦幀改為合併至空槽位之內，上限便不再造成過時格子，於是改為 200，此時空槽位會先成為約束。在某個畫面尺寸下成立的發現，並不是關於編碼器的發現
- **反銳化遮罩**：被比下去。銳化 0.8 花 2,692 字節得 0.00678，而重用 0.006 花 2,664 字節得 0.00653
- **從整個 64 色網格選取調色盤項目**：全部 180 次擬合的項目都相同。幀本身已量化至該網格上，所以中心點與投影形心收斂一致
- **色度權重由 1.0 降至 0.25**：完全持平
- **在線性光中抖動**：每個模糊指標都偏好在其自身空間中進行的抖動：在 Oklab 中模糊時為 0.0260 對 0.0408，在線性光中模糊時為 0.0370 對 0.0302，均為卡通。渲染出來，卡通的樹變成橙紅色，天空出現色塊；遊戲片段上則好壞參半。保持關閉
- **8x8 Bayer 矩陣，或 8x8 藍雜訊遮罩**：卡通上持平，遊戲片段上較差，0.0424 及 0.0431 對比 0.0412
- **精確調色盤擬合，把每個格子的顏色裝入兩個調色盤**：在 143 個卡通幀中應用於 42 個，99 個遊戲幀中應用於 1 個，卡通上較差，0.0265 對 0.0258，記憶庫 43 個對 37 個
- **保護保留的調色盤，使沒有格子比全新擬合時更差**：保留的幀較少，失去大部分得益：遊戲片段 0.0376 對比不設保護的 0.0365，嚴重偏差的格子更多，129 對 122
- **在模糊視圖上重用常駐圖案**：在相同記憶庫數目下，遊戲片段好 9 至 12%，但在卡通上，重用搜尋把它換成少九個記憶庫及更差的誤差。好壞參半，保持關閉
- **由 pngquant 選擇兩個調色盤**：兩段片頭全部 59 幀都比擬合出的調色盤差，卡通模糊後誤差 0.0287 對 0.0154，遊戲片段 0.0266 對 0.0201。它為每幅圖像優化一個不受限的調色盤，之後還要吸附到 64 種顏色上
- **ImageMagick 以 Floyd-Steinberg 抖動至 64 種顏色**：在遊戲片段的單一靜止幀上勝出，0.0151 對 0.0169，但在烘焙中落敗：卡通 0.0337 對 0.0262，遊戲片段 0.0353 對 0.0258，記憶庫 19 個對 12 個。圖樣每幀都在變，圖塊不再重複，合併因而增加
- **按使用格子數目為合併圖塊播種及作選擇**：好壞參半。遊戲片段上合併格子較少，但卡通上較差，嚴重偏差的格子 16 個對 8 個，而在這項改動所針對的淡入淡出處亦沒有改善

### 保留的方案

- **整幀寫入，以舊的 26 週期迴圈量度**：9.10 至 20.35 fps，單項最大得益
- **常駐圖案重用**：4.07 至 15.77 fps，誤差更低
- **卡通而非真人實拍來源**：誤差低 44%
- **每次烘焙量度降噪**：最多 8%，沒有任何常數勝過它
- **保留上一幀的調色盤**：只有當保留調色盤的誤差比全新擬合高出 30% 以上，才以全新擬合取代。遊戲片段：模糊後誤差 0.0397 降至 0.0347，嚴重偏差的格子 418 降至 100，記憶庫 40 降至 24。卡通：0.0258 降至 0.0249，記憶庫 37 降至 26。重新擬合會為每個常駐圖塊重新著色，令靜止區域偏移，值得重用的常駐圖塊亦隨之減少
- **只在各調色盤之內合併圖塊**：合併後的格子透過自己的調色盤繪製替代圖塊，而合併過去會給它一個取自另一調色盤格子的圖塊，其索引於是以錯誤顏色繪出：這些就是繁忙時刻出現的雜散圖塊。嚴重錯誤的格子在人群片段由 707 降至 1，遊戲片段由 340 降至 5，卡通由 8 降至 0
- **不留任何嚴重錯誤的格子**：格子與來源的平均 Oklab 距離超過 0.25 即屬嚴重錯誤。合併後，凡替代圖塊會越過此線的格子都會取得自己的圖塊，由最差的開始；若某調色盤仍有這類格子，便向另一調色盤借用槽位；每一步只在令數目下降時才保留。在這裏每部影片的十二個五秒時段中，包括遊戲、卡通、人群、城市、鳥類及 3D，數目都是零。以來源而非格子自身圖塊作量度基準，因為兩種誤差會疊加
- **合併後的格子若有更接近的、已在螢幕上的圖塊，便改用它**：螢幕上那一幀仍在使用的圖塊，這一幀不能覆寫，所以指向它們毫無代價。合併後的格子只在逐像素及經相同模糊後都更接近時才切換；遊戲片段最差十分之一的幀由 0.0294 降至 0.0284，串流由 19 個記憶庫降至 17 個；人群片段最差的幀由 0.0540 降至 0.0494，記憶庫由 27 降至 21。若只憑模糊視圖便容許切換，嚴重偏差的格子會更多，363 對 22，並在某個遊戲幀上留下一條錯誤圖塊帶
- **以每幀誤差的第 90 百分位數選擇重用值**：平均值會讓一個在切鏡處令那一幀拖影的閾值勝出；卡通最差的幀由 0.0412 回落至 0.0297
- **以重播出的畫面對比未降噪參照為降噪評分，並在接近打和時偏向較便宜的設定**：調色盤沿用曾令兩項搜尋漂移至勝出 1 至 2%、但合併格子多一倍的設定。卡通最差的幀由 0.0420 回落至 0.0303，嚴重偏差的格子由 142 降至 8；遊戲片段淡出結尾處損毀的 HUD 已消失
- **在每個格子的模糊視圖上合併圖塊**：遊戲片段模糊後誤差由 0.0412 降至 0.0394，代價是 39 個記憶庫中的一個，卡通持平。有了抖動，兩個看似相同的圖塊可能大部分像素都不同，所以逐像素距離會把抖動合併到錯誤的圖塊

降噪之所以量度而非固定，是因為合適的強度是片段本身的屬性。同一部影片的三個十五秒時段偏好三種不同強度，最佳與最差選擇之間相差 8%。

### 一個卡帶的成本

在回歸測試集上量度，12 fps、256 乘 192、全強度抖動、兩秒時段，所以每多或少一個記憶庫，每秒記憶庫數便相差半個：

| 片段 | 類型 | 每秒記憶庫數 | 62 個記憶庫可容納 |
|---|---|---|---|
| 合成方塊場 | 合成 | 6.0 | 10s |
| Sintel 預告片 | 3D 動畫 | 4.0 | 15s |
| Popeye for President | 手繪卡通 | 3.0 | 20s |
| Vespero en Hong Kong | 真人實拍 | 6.0 | 10s |
| Cute Colorful Bird | 動物 | 5.0 | 12s |
| Bhagoria 舞蹈 | 人物 | 6.0 | 10s |

成本隨片段的變化遠大於隨任何設定的變化，因此只應比較來自同一來源時段的兩個卡帶。這裏沒有任何機制會為遷就容量而縮短影片：使用 `--fps auto` 時，烘焙器會調低幀率直至影片放得下；使用固定幀率時，它只報告可容納的播放時長，然後停止。

## 驗證

播放器已於 2026-10-17 在 Master System 及 Game Gear 上運行，未見任何缺陷。這裏每個數字仍然來自模擬器、組譯清單或重播驗證模型：遊戲機上的運行顯示畫面沒有問題，但不量度任何東西。

| 檢查 | 所確立的事項 |
|---|---|
| 重播驗證模型 | 烘焙器對串流的模型能重播出編碼器預期的畫面，精確至小數點後五位 |
| mednafen 擷取 | 從 mednafen 擷取的幀與重播驗證模型逐像素相符，因此該模型可代表螢幕 |
| `make timing` | 編譯後播放器中每對 VDP 寫入的間隔都達到 29 T-states，在受保護的垂直消隱複製內則為 16，並把所有組譯清單當作同一程式逐一走遍 |
| `test_seek_on_z80.py` | 建置好的播放器為左右鍵選出正確的跳轉點，跳轉後重播位於該點的記憶庫及偏移 |
| `test_diag_on_z80.py` | 建置好的診斷資訊在 Z80 上對着 VDP 模型執行，幀、記憶庫及押後場數兩行寫在位置疊加層的精靈之後 |
| `test_osd_on_z80.py` | 建置好的位置疊加層在 Z80 上對着 VDP 模型執行，已播放時間、總時間、位置列、狀態符號及其調色盤都寫到精靈讀取的位置，工作分散到多個場而不越過幀中斷 |
| `test_transport_on_z80.py` | 建置好的操控判定在 Z80 上執行，檢查每個按鍵的作用、疊加層顯示多久，以及甚麼能喚醒已停止的播放器 |
| `test_replay_on_z80.py` | 建置好的重播程式在 Z80 上執行，V 計數器固定於選定的行，沒有任何調色盤字節或切換在時窗以外到達 VDP |
| 回歸測試集 | 六部不同類型的影片在每次測試時烘焙，各自須符合量度出的誤差及記憶庫預算 |

### 在真實硬件上

2026-10-17，擁有者在 Master System 及附 Everdrive 的 Game Gear 上運行播放器，未見任何缺陷。兩部遊戲機能確立的東西不同：

| 主張 | Master System | Game Gear |
|---|---|---|
| 傳輸迴圈中的 VDP 寫入間隔 | 能 | 能：相同 VDP 核心、相同時脈 |
| 播放期間繪製的疊加層及診斷資訊 | 能 | 能：它們的寫入經由同樣的限速路徑 |
| PSG 發出的聲音 | 能 | 能：同一枚晶片 |
| 顏色 | 能 | 不能：Game Gear 會把調色盤重新對應到它自己的顏色 |
| 螢幕邊緣 | 能 | 不能：在 Master System 模式下它只顯示中央 160x144 |

兩次運行用的都是 Master System 卡帶。原生的 Game Gear 卡帶尚未在遊戲機上運行。

沒有任何模擬器強制執行 VDP 寫入間隔，因此下一次對傳輸迴圈的改動，在再次於硬件上運行之前都屬未驗證，不論本機數字看來多好。

## 開發

安裝一次 pre-commit hook。每次提交時，它會執行格式化工具、linter、型別檢查器及附覆蓋率下限的測試套件；若暫存的路徑可能影響播放器，它亦會建置 ROM，並執行靜態分析、時序閘門及 Z80 重播：

```bash
make hooks
```

```bash
# 格式化
uv --project tools run ruff format tools/

# Lint 閘門
uv --project tools run ruff check tools/

# 型別閘門
uv --project tools run mypy tools/smsggmedia tools/scripts

# 測試，附 95% 覆蓋率下限
uv --project tools run python -m pytest tools/tests --cov=smsggmedia --cov=tools/scripts --cov-config=tools/pyproject.toml --cov-fail-under=95

# 下載並驗證回歸測試影片
uv --project tools run python tools/scripts/fetch_clips.py

# 在版本固定的映像內執行的播放器閘門
make rom
make analyse
make timing
```

回歸測試集刻意烘焙六段不同類型的片段。它們不在儲存庫內，我們亦無權再分發，所以清單只記錄其身分，由上述腳本下載並驗證。沒有它們時，只有已提交的合成片段會運行，閘門亦弱得多。所有鳴謝及授權均列於 [`tools/clips.manifest.json`](tools/clips.manifest.json)。

### 穩定性

1.0 之前不作任何承諾，次版本亦可能破壞以下任何一項。由 1.0 起會承諾以下介面：

| 介面 | 承諾 |
|:--------|:--------|
| `python -m smsggmedia.cartridge <source>` | 唯一的指令。它的參數保持名稱及意思不變 |
| `--bundle DIR` | 輸出一個可直接嵌入的資料夾，其結構保持名稱不變：`DIR/src/`、`DIR/include/fmv/`、`DIR/movie/`、`DIR/fmv.mk`、`DIR/target.mk`、`DIR/README.md` |
| `build/smsggmedia.sms` | 卡帶輸出的位置及其名稱 |
| 結束碼 | 成功時為 0，失敗時為非 0 |

C 程式庫對外的介面是 [`include/fmv/`](include/fmv) 內的標頭檔。[`src/`](src) 下的一切都屬內部實作，可能隨時改動而不另行通知。

## 常見問題

<details>
<summary><strong>為何圖塊要換入換出，而不是存放在 ROM？</strong></summary>
<br>

Master System 只從 VRAM 繪圖，而 VRAM 可容納 512 個圖案。一部影片需要數以千計，所以它們存放在卡帶中，播放器把每幀的新圖案複製到螢幕沒有顯示的槽位。

</details>

<details>
<summary><strong>能在 Game Gear 上運行嗎？</strong></summary>
<br>

能，有兩種方式。`--target gg` 建置原生的 Game Gear 卡帶，使用完整的 160x144 螢幕、4096 色調色盤及耳機立體聲，目前只在 mednafen 中運行過。附 Everdrive 的 Game Gear 亦可運行 Master System 卡帶，寫入時序正是這樣檢查的；在那個模式下它只顯示畫面中央 160x144 的部分，並重新對應調色盤。

</details>

<details>
<summary><strong>能在 PAL 遊戲機上播放嗎？</strong></summary>
<br>

它按 NTSC 節奏，每秒 59.92 場。播放器每場繪製一個區塊，因此 50 Hz 的遊戲機會以約為預定速度六分之五的速度播放同一串流。這裏未曾在任何 PAL 遊戲機上作檢查。

</details>

<details>
<summary><strong>聲音聽起來是怎樣的？</strong></summary>
<br>

PSG 有三個方波音調聲道及一個噪音聲道，沒有取樣聲道。烘焙器追隨音軌中最強的三個音符及響度，因此清晰的旋律能傳達出來，而對白會變成音調。經由音量暫存器播放取樣會較接近原聲，但會佔用傳輸迴圈的時間，而這些時間現時由畫面使用。

</details>
